# SPHEREx Scientific Service & Archive Tools

This package provides the scientific processing and minimal HTTP API (Milestone M2) for the SPHEREx Time Machine project (NASA Space Apps Challenge 2026, *Planet X and SPHEREx*).

It serves real, WCS-aligned Level 2 SPHEREx spectral-image observations from NASA/IPAC IRSA, preserving astronomical units, detector information, observation dates, validity quality masks, and provenance. It never substitutes synthetic data for real requests.

---

## Quickstart

From the `server/` directory, using [uv](https://docs.astral.sh/uv/) and Python ≥3.14:

```bash
cd server
uv sync --locked
uv run --locked pytest -v
```

### 1. Start the Scientific API (FastAPI)

```bash
uv run --locked uvicorn spherex.api:app --host 0.0.0.0 --port 8000
```

With auto-reload for local development:

```bash
uv run --locked uvicorn spherex.api:app --reload --port 8000
```

### 2. Endpoints

- **`GET /health`**: Service status, version, and confirmation of cached scientific products.
  ```bash
  curl -s http://127.0.0.1:8000/health
  ```
- **`GET /datasets`**, **`GET /datasets/{id}/frames`**: M4.5 inventory and fixed
  prepared comparisons (`m101`, `wise0855-d6`, `barnard-d2`, `barnard-d6`).
  Known missing/corrupt cases return explicit 503; unknown IDs return 404.
  These endpoints never download products or substitute synthetic observations.
- **`GET /frames?ra=<deg>&dec=<deg>&fov=<arcmin>`**: Retrieve WCS-aligned real observation frames.
  ```bash
  # Query verified M101 observation pair (Detector 2, ~1.49 µm, 37.68 days apart)
  curl -s "http://127.0.0.1:8000/frames?ra=210.80227&dec=54.34895&fov=3.0"
  ```

## Package Architecture (`spherex/`)

- **`spherex.archive`**: SIA2 discovery queries, IBE cutout URL formulation, bounded HTTP retrieval with socket/read timeouts, and SHA-256 verified caching.
- **`spherex.fits`**: FITS header inspection, quality flag bitmap decoding (`MSKN*`), UTC/MJD timestamp verification (`DATE-OBS` vs `DATE` HDU creation), and `Observation` dataclass.
- **`spherex.alignment`**: WCS TAN-SIP handling, common-grid reprojection (`reproject_interp`), approximate wavelength matching (WCS-WAVE), validity mask intersections, and FITS/PNG export.
- **`spherex.models`**: Pydantic schemas corresponding to `frontend/lib/types.ts` (`FramesResponseModel`, `FrameModel`, `WCSModel`, `BandInfoModel`, `FrameStatsModel`, `TargetModel`).
- **`spherex.service`**: Region proximity matching, data loading from cached `aligned.fits` and `manifest.json`, coordinate orientation transformation (`np.flipud`), and error handling (`UnsupportedRegionError`, `DataUnavailableError`).
- **`spherex.api`**: FastAPI application with CORS middleware, structured error responses, and endpoints.
- **`spherex.prepare`**: Reproducible data preparation CLI.
- **`scripts/validate_irsa.py`**: Standalone M1 validation CLI, refactored to delegate to `spherex.*` while maintaining 100% backward compatibility for existing scripts and tests.

## Reproducible Data Preparation

### M4.5 additional cases (independent of M101)

```bash
# Repeat for barnard-d2 and barnard-d6; uses only two pinned M4 products per case.
uv run --locked python -m spherex.datasets --dataset wise0855-d6 --research-dir outputs/m4 --offline
# Without a research cache, explicitly allow bounded downloads of the pinned pair:
uv run --locked python -m spherex.datasets --dataset wise0855-d6 --timeout 30
```

Default M4.5 products live in `outputs/datasets/<id>`; configure API and preparation
with `SPHEREX_DATASETS_DIR` to relocate the root. `--output` overrides one case's
preparation directory. Neither this root nor failed optional preparation changes
`SPHEREX_DATA_DIR`, `/frames` or M101 startup. Repeated valid preparation is
idempotent. No SIA/catalog search happens in this CLI or in HTTP requests.

`data/datasets.json` is separate from catalog candidates. Small packaged evidence
in `data/dataset-evidence.json` is regenerated by
`uv run --locked python scripts/export_dataset_evidence.py`; tests check it
against the original `docs/m4-evidence.json`. Raw FITS remain ignored.
Scientific labels, exact commands, Docker profile and verification limits:
[`docs/m45-scientific-cases.md`](../docs/m45-scientific-cases.md).

### Existing M101 preparation

To prepare or verify the validated M101 observation dataset:

```bash
# Verify existing cache (or prepare from scratch)
uv run --locked python -m spherex.prepare --output outputs/m101

# Replay offline without network access using verified local cutouts & discovery XML
uv run --locked python -m spherex.prepare --output outputs/m101 --offline

# Force re-running pipeline
uv run --locked python -m spherex.prepare --output outputs/m101 --force
```

Alternatively, invoke the standalone CLI:

```bash
uv run --locked python scripts/validate_irsa.py \
  --ra 210.80227 --dec 54.34895 --detector 2 --output outputs/m101
```

## Testing

Run all unit tests and integration tests:

```bash
uv run --locked pytest -v
```

The test suite covers:
- `tests/test_api.py`: FastAPI endpoints (`/health`, `/frames`), Pydantic validation, 422 on invalid coordinates, 404 on unsupported regions, 503 on missing data, array serialization, and canvas orientation.
- `tests/test_modules.py`: Unit tests for `archive`, `fits`, and `alignment` functions.
- `tests/test_data_validation.py`: The original 25 M1 verification tests for bounds, quality bitmasks, timestamps, WCS geometry, and reprojection.

## Orientation & Serialization

- **On disk (`aligned.fits`)**: Follows standard astronomical FITS conventions (row 0 is South, `CDELT2 > 0`, `origin='lower'`).
- **In API JSON (`pixelData`)**: Formatted for web canvas and `frontend/lib/wcs.ts` (row 0 is North/top, column 0 is East/left, `np.flipud(fits_array)`). Non-finite values (`NaN`) are set to `0.0` with a matching `1`/`0` binary `validMask` so standard JSON parsers and browser `Float32Array` buffers operate without errors.
- **Display units**: Calibrated surface brightness in `MJy / sr`.

## Scientific Limitations

1. **WCS-WAVE Solution**: Uses the archive's approximate visualization wavelength solution, not precision CWAVE/CBAND calibration.
2. **Static Field Visualization**: The M101 demonstration showcases two spectrally compatible, time-separated epochs of an extended galaxy; it is not a claim of moving-object detection, variability discovery, or Planet X.
3. **Background & Noise**: Science images include zodiacal light; no background model subtraction or PSF homogenization is performed.

## M4: bounded moving-target feasibility research

This independent CLI leaves the M1 defaults, M101 API, frontend and Docker
initialization unchanged. Run from `server/`:

```bash
uv run --locked python -m spherex.research --timeout 20
uv run --locked python -m spherex.research --offline
# Optional alternative, after evaluating the primary candidates:
uv run --locked python -m spherex.research --targets lalande21185 --timeout 30
uv run --locked python -m spherex.research --targets lalande21185 --offline
uv run --locked pytest -q
```

The default targets are Barnard's Star, WISE 0855−0714 and Epsilon Indi B.
`spherex/data/m4-targets.json` records their catalog identifiers, position epochs,
proper-motion convention, uncertainties, references and detector rationale.
Epsilon B requires an actual 2MASS row including its observation Julian date;
Lalande requires an actual Gaia DR3 row. Failed catalog access blocks that target.
No frontend preset supplies scientific astrometry.

Outputs live under `outputs/m4/<target>/d<detector>/`, separately from M101:
raw SIA XML and query sidecars, hash-verified real cutouts, inspection metadata,
all pair decisions, optional validated comparison FITS/PNGs, latest manifests
and timestamped `runs/*.json` histories. The campaign root also has a manifest.
Offline mode requires exact query URL/hash agreement and verified cached FITS;
it never contacts the archive or substitutes synthetic data. Missing files and
remote/OVERFLOW results classify research as incomplete, not an empty archive.
To reproduce a nondefault sample offline, repeat the same target, date, field
size and `--max-downloads` arguments with `--offline`.

Discovery covers a sampled 2025–2027 trajectory (configurable MJD interval,
maximum 1000 days) using a cone of at most 0.03 degrees, with a 36 arcsec margin.
One fixed sky center is used for all dates. Native cutouts are padded to twice
the comparison side (1–5 arcmin); positions are propagated to actual FITS epochs.
Annual observer parallax, orbital photocenter motion and covariance propagation
are not implemented. Their uncertainties remain explicit limitations.

Acceptance thresholds cannot be relaxed from this CLI: at least 30 days,
80% common valid/spectrally matched grid, wavelength offset at most 0.25 local
bandwidths, bandwidth ratio at most 1.2, and unchanged conservative flags.
At most 24 products per detector, two detectors per primary target and one for
the alternative are inspected. Downloads are sequential, each <=16 MiB, with
bounded query sizes/timeouts, existing per-directory cache limits, and a global
192-product/2 GiB downloaded-product ceiling including existing campaign cache.
The budget reserves the maximum next file size; exhaustion is incomplete research.

Every pair is evaluated, including those after the first acceptable pair. One
comparison figure per detector is saved only if it passes; a separate figure
labels both catalog positions **PREDICTED**. Native variance and local background
contrast are exploratory diagnostics, not calibrated photometric SNR. Valid
predicted pixels do not establish source identity, signal, or freedom from
confusion, and no measured motion is reported.

Exit codes: `0` = completed campaign with a comparable pair, `2` = completed
negative bounded sample, `3` = incomplete/blocked research, even if some pairs
passed. Review `accepted_pairs`, each `motion_status` and local diagnostics in
the manifests, not just the exit code. Evidence and dataset-registry proposal:
[`docs/m4-target-feasibility.md`](../docs/m4-target-feasibility.md).
